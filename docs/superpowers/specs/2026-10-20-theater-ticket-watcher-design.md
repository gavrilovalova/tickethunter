# Спек: бот-ловец билетов в театр Вахтангова

Дата: 2026-10-20 · Статус: на ревью у Кати

## Цель

Личный инструмент для Кати: следить за страницами спектаклей на vakhtangov.ru и присылать в Telegram уведомление со ссылкой на покупку, как только на отслеживаемый спектакль появились билеты (кто-то сдал) или открылась новая дата с билетами в продаже. Допустимая задержка уведомления — до 5–10 минут.

Успех: Катя узнаёт о появившихся билетах в пределах одного цикла проверки и может купить их по ссылке в один тап с телефона.

## Скоуп

В скоупе: один сайт (vakhtangov.ru), один пользователь (личный chat_id Кати), Telegram как единственный интерфейс.

Вне скоупа: другие театры (парсер изолирован, чтобы адаптеры добавлялись позже), мультипользовательность, автоматическая покупка, отслеживание цен, веб-интерфейс.

## Архитектура

GitHub-репозиторий c GitHub Actions workflow, запускаемым по schedule каждые 5 минут (плюс `workflow_dispatch` для ручного запуска). Постоянного сервера нет. Один запуск — один проход Python-скрипта.

Компоненты (модули одного пакета `watcher/`):

- `telegram.py` — обёртка над Bot API: `getUpdates` (с offset), `sendMessage` (с inline-кнопками), `answerCallbackQuery`. Ничего не знает про билеты.
- `parser_vakhtangov.py` — принимает HTML страницы спектакля, возвращает название и список сеансов `(stage, datetime, status, buy_url)`. Ничего не знает про Telegram и состояние.
- `state.py` — чтение/запись `state.json`, типизированная модель состояния.
- `engine.py` — сравнение нового снимка сеансов с прошлым, вычисление событий-уведомлений (чистая функция: вход — старое и новое состояние, выход — список событий).
- `main.py` — оркестрация одного запуска.

Состояние хранится в `state.json` в том же репозитории; workflow коммитит его обратно при изменении. В workflow включён `concurrency` group, чтобы два запуска не работали одновременно.

Секреты в GitHub Secrets: `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`.

## Поток одного запуска

1. **Команды из Telegram.** `getUpdates` с offset из состояния. Сообщения не от `TELEGRAM_CHAT_ID` игнорируются молча. Обрабатываются:
   - сообщение с URL вида `vakhtangov.ru/show/...` → добавить подписку (скачать страницу, взять название), ответить «✅ Слежу за „Маскарадом"» с текущим статусом дат;
   - `/list` → список подписок, по каждой — даты со статусами и inline-кнопка «Удалить»;
   - нажатие кнопки «Удалить» → убрать подписку, подтвердить;
   - всё остальное → короткая подсказка, что бот умеет.
2. **Проверка подписок.** Для каждой подписки: скачать страницу (httpx, таймаут 20 с, человеческий User-Agent), распарсить сеансы.
3. **Вычисление событий** (engine, по каждому сеансу):
   - был `sold_out` → стал `available`: событие «появились билеты»;
   - новый сеанс со статусом `available`: событие «новая дата, билеты в продаже»;
   - новый сеанс `sold_out`: запомнить молча;
   - был `available` → стал `sold_out`: обновить молча (это взводит триггер заново — следующее появление билетов снова даст уведомление);
   - дата сеанса в прошлом: удалить из состояния молча.
4. **Уведомления.** На каждое событие — сообщение: название спектакля, дата, день недели, время, сцена; inline-кнопка «Купить» со ссылкой на `vakhtangov.ru/tickets/buy/?...`; ниже ссылка на страницу спектакля. Повторных уведомлений по сеансу нет, пока его статус не пройдёт цикл `available → sold_out → available`.
5. **Коммит состояния**, если оно изменилось.

## Модель состояния (`state.json`)

```json
{
  "telegram_offset": 123456,
  "subscriptions": {
    "https://vakhtangov.ru/show/maskarade/": {
      "title": "Маскарад",
      "added_at": "2026-10-20T12:00:00+03:00",
      "parse_error_notified": false,
      "sessions": {
        "main|2026-11-26T19:00": { "status": "sold_out", "buy_url": null },
        "main|2026-12-26T19:00": { "status": "available", "buy_url": "https://vakhtangov.ru/tickets/buy/?stageuid=main&datetime=2026-12-26-19-00-00" }
      }
    }
  }
}
```

Ключ сеанса — `stageuid|datetime`, чтобы одинаковое время на разных сценах не схлопывалось.

## Парсер vakhtangov.ru

Вход — HTML страницы спектакля. Разметка: блоки по сценам (заголовок «Основная сцена» и т.п.), внутри — строки сеансов с датой и временем. Статус сеанса: есть ссылка «Купить билеты» на `/tickets/buy/` → `available` (href становится `buy_url`); текст «Билеты закончились» → `sold_out`. Название спектакля — из заголовка страницы. `stageuid` берётся из параметра `stageuid` в buy-ссылках блока; для sold-out блока без единой ссылки — нормализованное имя сцены.

Если страница скачалась (HTTP 200), но не найдено ни одного блока сеансов и ни одного маркера статуса — это parse error, а не «нет дат»: сайт мог поменять вёрстку.

## Обработка ошибок

- Сетевая ошибка, таймаут, 5xx при проверке подписки: пропустить её в этом цикле, состояние не менять, уведомление не слать.
- Parse error: однократное уведомление «⚠️ Не могу прочитать страницу <название> — возможно, сайт изменился» (флаг `parse_error_notified`), сбрасывается при первом успешном парсинге.
- Ошибка Telegram API при отправке: один повтор; если снова неудача — залогировать и продолжить (состояние по этому событию не фиксировать, чтобы уведомление повторилось в следующем цикле).
- Невалидная ссылка от пользователя (не vakhtangov.ru/show/): ответить, что пока умею только страницы спектаклей Вахтанговского.
- Падение всего запуска видно в GitHub Actions (история ранов).

## Тестирование

pytest. Снапшоты HTML страницы спектакля в `tests/fixtures/`: вариант «все даты sold out», «есть билеты», «смешанный». Тесты:

- парсер на каждом снапшоте даёт ожидаемый список сеансов;
- engine: все пять переходов из «Вычисления событий», включая антиспам-цикл;
- обработка команд (URL, `/list`, удаление) с замоканным Telegram и фиктивным состоянием;
- parse error поднимается на HTML без блока сеансов.

## Ограничения и риски

- GitHub cron не гарантирует точность: реальный интервал 5–12 минут — в пределах допуска Кати, но единичный сданный билет, купленный за 2 минуты, поймать не всегда получится. Путь апгрейда — перенос воркера на Railway с минутным интервалом, архитектура это позволяет (меняется только запуск).
- Ответ бота на команды приходит с задержкой до одного цикла — осознанный компромисс за бесплатность.
- Парсер привязан к вёрстке сайта; поломка ловится parse-error-уведомлением.
- Быстрее самого сайта театра узнать нельзя: если театр обновляет статус с задержкой, она добавляется к нашей.
